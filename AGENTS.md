# Работа над «Анютой»

## Контекст
- Android, Kotlin, Jetpack Compose; один модуль `app`, пакет `ru.family.rasti`.
- JDK 17, Gradle Wrapper; версии SDK и библиотек — в `app/build.gradle.kts`.
- Данные ребёнка хранятся локально и в отдельном приватном GitHub-репозитории.
- Краткая карта кода и формата данных: `docs/architecture.md`.
- Команды и сценарии проверки: `docs/testing.md`.

## Экономия контекста
- Начинай с `git status --short`, затем ищи нужные символы через `rg`.
- Читай карту архитектуры и конкретные участки кода по задаче; не весь проект.
- Не загружай целиком README, историю релизов, CSV WHO и логи без необходимости.
- Не исследуй `.git`, `.gradle`, `.kotlin`, `build`, `.tmp-who`, `.codex-run-*`
  и `.local` при обычном поиске исходников.
- Полные логи сохраняй локально; в ответ выводи причину сбоя и короткий итог.
- Используй `tools/check.ps1`, а не восстанавливай команды сборки по истории чата.
- Для известной Windows-ошибки Java loopback используй `-WindowsSocketFallback`;
  для ClassNotFoundException из пути на кириллице — `-BuildRoot` с путём на латинице.
  Подробности и расположение отчётов — в `docs/testing.md`.
- Не запускай повторно прошедшие проверки без новых правок или конкретной причины.
- Не добавляй плагины, зависимости и несколько агентов ради простой задачи.
- Подбирай глубину анализа к риску: расчёты, данные и синхронизация требуют
  проверки граничных случаев; правка текста не требует нового набора тестов.
- В итоговом ответе укажи изменения, фактически выполненные проверки и ограничения.
- Не обещай процент экономии токенов без сравнимых замеров.

## Качество изменений
- Делай минимальное связное изменение; не смешивай его с общим рефакторингом.
- При изменении большого файла выноси самостоятельную ответственность, если это
  уменьшает сложность задачи. Размер около 500 строк — повод оценить разделение,
  а не обязательство переписать файл или искусственно разбить его на части.
- Расчёты и объединение данных должны оставаться проверяемыми вне интерфейса.
- Сначала запускай тесты изменённой области; перед завершением правок Kotlin,
  ресурсов или сборки — полный режим `tools/check.ps1 -Mode Full`.
- Для исправления существенной ошибки добавляй тест исходного сбойного сценария.
- Для UI проверяй светлую/тёмную темы, узкую ширину и увеличенный шрифт;
  правила снимков и ручной проверки описаны в `docs/testing.md`.
- Не обновляй визуальные эталоны только ради зелёного теста: сначала изучи разницу.
- Если окружение блокирует проверку, сообщи точную причину; не называй её пройденной.

## Сохранность данных
- Не подменяй повреждённые данные пустыми и не синхронизируй их как новый дневник.
- Запись должна быть атомарной; сохраняй проверенную резервную копию.
- Не удаляй повреждённый оригинал при восстановлении без сохранения его копии.
- Сохраняй ID, timestamps и отметки удаления при merge и переносе между днями.
- Учитывай изменения пользователя, сделанные во время сетевого запроса.
- Тесты используют синтетические данные и поддельный транспорт, без настоящих
  GitHub/MAX-токенов, семейного репозитория и отправки сообщений.
- Никогда не включай токены, ключи подписи, личные данные и сетевые тела в логи,
  тестовые эталоны, документацию или коммиты.
- Не меняй медицинские справочные значения без проверки первичного источника.
- Релизный тег и публикация APK — отдельное действие по запросу пользователя.

## Актуальность документации
- README описывает текущее поведение; история версий находится в CHANGELOG.md.
- При изменении потоков данных/ответственности обновляй `docs/architecture.md`.
- При изменении сборки/тестов обновляй скрипт проверок и `docs/testing.md`.
- Изменения пользовательского поведения добавляй в раздел Unreleased CHANGELOG.
- Не дублируй подробную документацию в AGENTS.md: оставляй короткие правила и ссылки.
